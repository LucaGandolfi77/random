# Capitolo 10 — La concorrenza: la verità atomica

**Parte II — Il centro tecnico, che chiude**

**Parole:** ~1.100

> "L'ottimizzazione prematura è la radice di ogni male."
>
> — Donald Knuth

La Parte II si chiude con il capitolo dove muoiono le certezze single-thread. Tutto ciò che precede questo capitolo era vero su un thread. Questo capitolo è la verità su molti thread, e la verità è più dura, e la durezza è la ragione per cui questo capitolo esiste: la concorrenza è il posto dove i bug smettono di essere *qui* e cominciano a essere *a volte, altrove, sotto carico, il terzo martedì*. Knuth ha detto che l'ottimizzazione prematura è la radice di ogni male, e aveva ragione, e la concorrenza fatta per performance prima della misura è l'arma più fine del male: è l'ottimizzazione che introduce bug che non puoi riprodurre. Questo capitolo insegna la verità, precisamente, e comincia con la race.

**La race, precisamente.** Una data race (gara sui dati) è: due thread, la stessa memoria, almeno uno che scrive, nessuna sincronizzazione. E la race è *comportamento indefinito* — non "risposta sbagliata": comportamento indefinito, la stessa classe del segfault, la stessa classe della lettura dell'indeterminato. Lo standard lo dice, e il dirlo dello standard è la cosa che cambia tutto: una data race non è un bug nel tuo programma; è la fine del significato del tuo programma.

```cpp
#include <thread>
#include <iostream>

int counter = 0;                              // condiviso, non sincronizzato: la race

void increment() {
    for (int i = 0; i < 100'000; ++i) {
        ++counter;                            // read-modify-write: tre passi, interleavabili
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join(); t2.join();
    std::cout << counter << '\n';             // 200.000? A volte 187.441. A volte 203.556.
                                              // E "a volte" è la parola peggiore dell'informatica.
    return 0;
}
```

`++counter` è tre passi: load, increment, store. Due thread intrecciano i passi, e l'intreccio perde incrementi, e la perdita è la race, e la race è comportamento indefinito — e *indefinito*, in questo caso, non è "il segfault": è *il numero sbagliato, a volte, sotto carico, al sito del cliente, il terzo martedì*, e l'"a volte" è la ragione per cui la race è la classe di bug peggiore dell'informatica: non è riproducibile quando la guardi. Il debugger è un osservatore, e l'osservare cambia il timing, e il timing cambiato fa sparire il bug. Heisenbug. Il bug che non c'è quando guardi.

**La correzione, precisamente: `std::atomic`.**

```cpp
#include <thread>
#include <atomic>
#include <iostream>

std::atomic<int> counter {0};                 // il tipo che non fa race

void increment() {
    for (int i = 0; i < 100'000; ++i) {
        ++counter;                            // read-modify-write atomico: un passo indivisibile
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join(); t2.join();
    std::cout << counter << '\n';             // 200.000. Sempre. Garantito. Dallo standard.
    return 0;
}
```

`std::atomic<int>` rende il read-modify-write indivisibile — a livello hardware, su x86, un'istruzione `lock add`; su ARM, load-link/store-conditionally — e l'indivisibilità è garantita dal *memory model*, che è la rivoluzione del C++11 di cui nessuno ringrazia: prima del 2011, il C++ non aveva memory model, e il C++ multithread era un umore del compilatore; dal 2011, è una specifica, e la specifica è la cosa che fa sì che `atomic` significhi qualcosa. Il risultato è 200.000. Sempre. L'"a volte" è morto.

**Il mutex, la correzione più grande.** Gli atomic sono per variabili singole. Per gli invarianti che attraversano molte variabili, il mutex:

```cpp
#include <thread>
#include <mutex>
#include <vector>

class Conto {
public:
    void deposita(int amount) {
        std::lock_guard lock(m_);             // RAII (capitolo 5): il lock è tenuto fino alla fine dello scope
        saldo_ += amount;                     // l'invariante: il saldo è sempre consistente sotto il lock
    }                                         // sbloccato QUI, automaticamente, ogni percorso, anche su throw
    int saldo() const {
        std::lock_guard lock(m_);
        return saldo_;
    }
private:
    std::mutex m_;
    int saldo_ {0};
};
```

`std::lock_guard` è RAII applicato ai lock — acquisito nel costruttore, rilasciato nel distruttore, ogni percorso, anche su eccezione — e il RAII è la ragione per cui i deadlock sono sopravvivibili: il lock non è mai dimenticato, e il dimenticare è la casa del deadlock. E il mutex protegge l'*invariante* — saldo più storia più tutto ciò che la classe sa — non solo la variabile, e il proteggere gli invarianti è la ragione per cui il mutex è il default e l'atomic è l'eccezione. La regola: **atomic per contatori singoli e flag; mutex per tutto ciò che ha più di una parte mobile.** E il corollario: tieni i lock per il tempo più breve possibile, e non chiamare mai codice sconosciuto mentre ne tieni uno — il codice sconosciuto potrebbe bloccare un altro mutex, e l'altro mutex potrebbe bloccare il tuo, e il bloccarsi a vicenda è il deadlock, e il deadlock è il cugino paziente della race: non indefinito, solo permanentemente bloccato, e il bloccarsi è almeno onesto.

**I thread, il modo moderno (C++20).**

```cpp
#include <thread>
#include <iostream>

int main() {
    std::jthread t([] {                      // jthread (C++20): fa join automaticamente, ed è cancellabile
        /* lavoro */
    });
    // niente t.join() necessario: il distruttore fa join. RAII, di nuovo, per i thread.
    return 0;
}
```

`std::jthread` è RAII per i thread — fa join nel distruttore, e il fare join è la cosa che chiude il bug "dimenticato il join → std::terminate" — e supporta la cancellazione (il `stop_token`), e la cancellazione è quella cooperativa, e la cooperativa è quella onesta: il thread decide quando fermarsi, e il decidere è la cosa che rende la cancellazione sicura.

Questo è il capitolo, e la Parte II si chiude. La race è comportamento indefinito; l'"a volte" è la parola peggiore dell'informatica. L'atomic rende una variabile indivisibile; il mutex protegge gli invarianti; `lock_guard` è RAII per i lock; `jthread` è RAII per i thread. E la verità più profonda: il memory model — dal 2011 — è ciò che fa sì che tutto questo *significhi* qualcosa, e il significare è la cosa che il compilatore implementa, e il compilatore la implementa sull'hardware, e l'hardware è x86 e ARM e RISC-V, e l'implementazione è il soggetto del capitolo 11: il rinascimento, lo stato dell'arte, la cadenza triennale — e la cadenza è la cosa che tiene il matrimonio interessante.
