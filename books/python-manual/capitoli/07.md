## Draft

Python doesn't hide errors. It raises them. When something goes wrong — when you divide by zero, when you open a file that doesn't exist, when you ask a list for an index that isn't there — Python stops and says: something broke.

This is not unkind. It is honest. You catch the error with `try`:

```python
try:
    result = 1600 / 0
except ZeroDivisionError:
    print("The measure is impossible.")
```

`try` is the admission that the world is not perfect. `except` is the gentle response. You don't have to fix everything. You just have to know that it broke. This is the first true sentence of a complex program: I know something went wrong, and I am still here.

`raise` is how you create your own errors:

```python
if hours < 0:
    raise ValueError("The hours cannot be negative.")
```

This is the question nobody asked: what if the number is wrong? You ask it yourself. You raise it. The error is named after its nature: `ValueError`, `TypeError`, `FileNotFoundError`. Naming the error is naming the fear.

`finally` is the thing that always happens, whether the error occurred or not:

```python
try:
    file = open("claims.txt")
except FileNotFoundError:
    print("No claims today.")
finally:
    print("The office closes at five.")
```

Even when the claim isn't there, the office closes. `finally` is the habit. It is the thing that doesn't count, but lasts.

Custom exceptions are when you define your own error class:

```python
class ClaimRejected(Exception):
    pass
```

Now you can raise `ClaimRejected`. It is the error that has a name, a story, and a memory. It is the claim that isn't settled.

## More examples

### Catching more than one error

You can catch different errors in the same block:

```python
try:
    amount = int("not a number")
except (ValueError, TypeError):
    print("The number is impossible to read.")
```

This is the interpreter that knows there are many ways to be wrong. It doesn't ask which one; it just catches them both.

### Custom exception with details

An error can carry its own information:

```python
class ClaimRejected(Exception):
    def __init__(self, claim_name, reason):
        self.claim_name = claim_name
        self.reason = reason
        super().__init__(f"{claim_name}: {reason}")

raise ClaimRejected("Joan Whitfield", "Flood depth exceeds limit")
```

This is the claim that explains why it was rejected. The error is not just a message; it is a story.

### The `with` statement: the file that closes itself

When you open a file, you want it to close, even if something breaks:

```python
with open("claims.txt", "r") as file:
    content = file.read()
```

`with` is the claim that has its own `finally`. It doesn't forget to close. It doesn't need to be reminded. It is the office that locks the door behind itself.

### The `assert`: the claim you assume is true

Sometimes you want to state what must be true, and stop if it isn't:

```python
hours = 1600
assert hours > 0, "The hours must be positive."
```

`assert` is the claim that doesn't ask politely. It says: this is the truth, or the program stops. It is the first thing you say that isn't false, turned into a guard.

### Errors inside loops

If you don't want a single error to stop the whole office, you catch inside the loop:

```python
claims = ["1600", "not a number", "800"]
results = []
for claim in claims:
    try:
        results.append(int(claim))
    except ValueError:
        results.append(0)
```

This is the office that continues working, even when one claim is broken. It doesn't let the broken claim stop the others.

### EAFP: asking forgiveness, not permission

Python encourages you to try first, then apologize if it fails (`EAFP` — Easier to Ask Forgiveness than Permission). You don't check if a file exists before opening it; you open it, and catch the error if it isn't there. This is the first true way of programming: act, then learn.
